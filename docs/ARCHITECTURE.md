# Архитектура LogisticsWeb

Документ описывает, как устроено приложение: слои, поток данных, алгоритм поиска маршрута, ограничения и точки расширения.

## 1. Общая картина

Приложение — монолит на ASP.NET Core 8 (Razor Pages). Никаких внешних сервисов, кроме публичного OSRM и тайлов OpenStreetMap, нет.

```

                │ HTTP (Razor Pages, form POST, fetch JSON)
┌───────────────▼─────────────────────────────────────────────────┐
│                       ASP.NET Core 8                            │
│                                                                 │
```

## 2. Слои и ответственность

| Слой | Файлы | Ответственность |

| Страницы | `Pages/Index.cshtml(.cs)`, `Pages/Clients.cshtml(.cs)` | Обработчики GET/POST, вью-модели, вызов репозитория и расчётного модуля |

### Модель данных

```csharp
public class Client
{
    public int Id { get; set; }
    public string FullName { get; set; }
    public string Address { get; set; }
    public string Coordinates { get; set; }   // "широта;долгота"
    public decimal OrderAmount { get; set; }
}
```

Координаты хранятся строкой `"lat;lon"` и разбираются в `Latitude`/`Longitude` при построении точек маршрута.

### Хранилище

`JsonClientRepository` реализует `IClientRepository` (`GetAllAsync`, `GetByIdAsync`, `AddAsync`, `UpdateAsync`, `DeleteAsync`) поверх одного JSON-файла:

- путь — `<ContentRoot>/App_Data/clients.json`, каталог создаётся при старте;
- операции синхронизированы через `lock` и сериализуются `System.Text.Json` с отступами (файл читаем глазами);
- `Id` выдаётся как `max(Id) + 1`.

Интерфейс существует именно для того, чтобы заменить файл на EF Core, не трогая страницы.

## 3. Поток данных при расчёте маршрута

1. **Формирование набора точек.** Один из трёх путей:
   - `OnPostGeneratePoints` — случайные 5–7 адресов из `AddressBook.Moscow` со случайными суммами заказов;
   - `OnPostImportClientsAsync` — клиенты из репозитория, у которых заданы координаты;
   - в обоих случаях первая точка — склад (`Базовый Склад`, 55.751244; 37.618423), `IsBase = true`.
2. **Сохранение в сессию.** Набор сериализуется в JSON и кладётся в `Session` под ключом `GeneratedPointsData` — так состояние переживает POST/Redirect и переходы между страницами.
3. **Матрица расстояний.** `BuildRoadDistanceMatrixAsync` для каждой пары точек запрашивает OSRM (`/route/v1/driving/...?overview=false`) и берёт `routes[0].distance / 1000`. При ошибке сети или не-2xx — хаверсин × 1.25 (эмпирический коэффициент извилистости дорог).
4. **Поиск лучшей комбинации.** DFS по всем подмножествам остановок с возвратом на склад, см. раздел 4.
5. **Отрисовка.** Сервер заполняет `RouteSteps` (этапы и деньги) и `MapPoints` (флаги `IsVisited`, `RouteOrder`); клиентский JS рисует маркеры (синий — склад, зелёный — в маршруте, красный — отброшен) и запрашивает полную геометрию маршрута у OSRM (`overview=full&geometries=geojson`) для линии со стрелками.

## 4. Алгоритм поиска маршрута

```
FindMostProfitableRouteDijkstra(points, distances):
    best ← пусто, bestProfit ← 0
    DFS(текущая точка = склад, пройдено = 0, доход = 0,
        маршрут = [], использованные = {склад})

DFS(cur, dist, revenue, route, used):
    полный_пробег ← dist + Dijkstra(cur → склад)
    profit ← revenue − полный_пробег × 900
    если profit лучше найденного (или равен при меньшем пробеге):
        best ← route
    для каждой неиспользованной точки next:
        used[next] ← true; route += next
        DFS(next, dist + Dijkstra(cur → next), revenue + доход[next], route, used)
        route −= next; used[next] ← false
```

**Ключевые решения:**

- **Критерий — прибыль, а не длина.** Маршрут может быть длиннее кратчайшего, если так он зарабатывает больше. Это и есть отличие от классической задачи коммивояжёра.
- **Подмножества, а не перестановки всех точек.** DFS перебирает варианты «кого вообще брать», поэтому заведомо убыточные клиенты естественно выпадают из лучшего решения; отброшенные точки остаются на карте красными.
- **Дейкстра вместо прямого обращения к матрице.** Участки считаются по матрице как по графу, что позволяет позже заменить полный граф на реальную дорожную сеть без переписывания поиска.
- **Сравнение при равенстве прибыли** — в пользу меньшего пробега, чтобы не выбирать «пустые» равноценные варианты.

**Сложность.** Число вариантов растёт как сумма по k от 1 до n−1 перестановок k точек: O(Σ P(n−1, k)) ≈ O(e·(n−1)!) по времени и O(n²) по памяти (матрица). Практический предел — 5–10 точек; для больших наборов нужен другой подход (см. раздел 6).

## 5. Состояние и сессии

- `AddDistributedMemoryCache()` + `AddSession()` с `IdleTimeout = 30 мин`, cookie `HttpOnly` и `IsEssential`.
- `UseSession()` обязан идти **до** `UseAuthorization()` — иначе `HttpContext.Session` недоступен (это отмечено комментарием в `Program.cs`).
- Набор точек живёт в сессии, клиентская база — в файле. Перезапуск приложения сбрасывает маршрут, но не клиентов.

## 6. Ограничения и направления развития

| Ограничение | Причина | Как исправить |
|---|---|---|
| Факториальный перебор | Полный DFS по комбинациям | 2-opt / 3-opt, динамическое программирование по подмножествам (Хелд–Карп), OR-Tools |
| Нет ограничений задачи | Модель не знает про время, вес, число машин | Добавить в модель `TimeWindow`, `Capacity`, `VehicleCount`; перейти к VRP-солверу |
| Запросы к OSRM по одному | Матрица строится в цикле `await` | Использовать OSRM `/table` (одна матрица), кэш и локальный инстанс |
| Файл вместо БД | Учебный масштаб | EF Core + SQLite/PostgreSQL, миграции |
| Нет тестов | Приоритет был у функциональности | Вынести расчёт в сервис `IRouteOptimizer` и покрыть unit-тестами на фиксированных матрицах |
| Нет авторизации | Локальный запуск | ASP.NET Core Identity, разделение данных по пользователю |
